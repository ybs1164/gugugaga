# 강화학습으로 AI 난이도 5단계 만들기 — 계획

작성일: 2026-11-03. 이 문서는 계획이다. 구현이 끝난 동작은 [`spec/game/ai.md`](spec/game/ai.md)와 새 CSV 명세로 옮기고, 이 문서는 설계 기록으로만 남긴다.

## 1. 목표와 원칙

- 빠른 한 판·샌드박스에서 AI 팀마다 **난이도 1(입문) ~ 5(최강)** 를 고른다.
- 모든 난이도는 같은 규칙·같은 시야로 둔다 — 구름 속 정보를 보거나 별을 더 받는 식의 **치트로 난이도를 만들지 않는다**([ai.md](spec/game/ai.md) 원칙 유지). 난이도 차이는 "얼마나 잘 두는가"에서만 나온다.
- 지금의 규칙 기반 AI(`EconomyAI`·`EnemyAI`·`FaithAI`)는 버리지 않는다. ① 합법 행동 후보를 만드는 틀, ② 모방 학습의 선생, ③ 평가 기준점(앵커), ④ 모델이 없을 때의 대체 동작으로 쓴다.
- CLAUDE.md 규칙을 지킨다: 모델 가중치·난이도 값은 `Data`(값만), 추론은 상태 없는 `Systems`, 난이도별 수치는 CSV 한 칸에 한 값, 화면 문구는 `Strings.csv`.
- 원문(Polytopia)의 봇 난이도는 단계 수가 다르다(위키 문서명 확인 필요 — `Bots`/`Difficulty` 페이지는 API에서 찾지 못함). 5단계로 두는 것은 "원문과 다른 점"으로 [ai.md](spec/game/ai.md)에 남긴다.

## 2. 핵심 설계: "후보 순위 정책"

이 게임은 한 턴에 유닛 이동·공격·건설·연구·훈련·신앙이 섞여 행동 공간이 매우 크다. 칸 단위 원시 행동(유닛 × 목적지 × 행동)을 그대로 강화학습하면 학습이 거의 진행되지 않는다. 그래서 **지금 AI가 이미 가진 결정 지점을 그대로 두고, 각 지점에서 "어느 후보를 고를지"만 학습**한다.

| 결정 지점 (현재 코드) | 후보 | "하지 않음" 후보 |
|---|---|---|
| 연구 `EconomyAI.Research` | 연구 가능한 기술 | 있음(별 모으기) |
| 훈련 `EconomyAI.Train` | (도시, 유닛 종류) | 있음 |
| 건설 `EconomyAI.Improve`·`PlanConnections` | (칸, 건설/채집 선택지) | 있음(이번 턴 건설 끝) |
| 보상 `EconomyAI.ChooseRewards` | 레벨업 보상 | 없음 |
| 배 업그레이드 `UpgradeRafts` | (뗏목, 배 종류) | 있음 |
| 신앙 `FaithAI.UsePunches`·`BuildTemple`·`UseMythicActive`·`Pray` | (펀치, 대상)·신전 칸·액티브 칸·기도 여부 | 있음 |
| 유닛 행동 `EnemyAI.RunTurn` (유닛마다) | 공격 대상 / 이동 목표 칸(목표 후보: 적·도시·점령·방어·탐험 가장자리) / 후퇴 칸 / 대기 | 있음 |
| 유닛 순서 | 아직 행동하지 않은 유닛 | — |

- 후보는 기존 System(합법성 검사 포함)이 만든다 → 모델은 **불법 행동을 낼 수 없다**.
- 정책 = 후보마다 점수를 매기는 작은 신경망, 결정 지점별로 softmax. 가치 함수(승률 추정)는 따로 하나.
- 결정 순서(경제 → 신앙 → 군사)는 [ai.md 한 턴의 순서](spec/game/ai.md#한-턴의-순서)를 유지한다. 순서까지 학습하는 것은 4단계 이후 선택 과제.

### 관찰(입력 특징)

팀 시야로 가린 상태만 쓴다(`VisionSystem` 기준, 구름 속 적은 0).

- **전역 특징**: 턴, 별·턴 수입, 도시 수·레벨 합, 유닛 수·종류별 수, 기술 수, 신앙·최대치, 점수(`ScoreSystem.ComputeBreakdown` 항목별), 보이는 적의 같은 값, 위협 여부(`EconomyAI.IsThreatened`).
- **후보 특징**: 후보마다 고정 길이 벡터 — 칸 지형·소유·건물, 내 수도/가장 가까운 적까지 거리, 그 칸을 칠 수 있는 적 수(`RetreatAfterAttack`과 같은 계산), 예상 피해·반격·처치 여부(`CombatSystem`), 별 비용, 지금 AI의 휴리스틱 점수(`EconomyAI.Score` 등 — 학습 초반을 크게 돕는다).
- 처음엔 손으로 만든 특징 + MLP로 시작한다(모바일 추론이 가볍다). 공간 정보가 부족하면 6단계에서 유닛 주변 크롭의 작은 CNN을 검토한다.

## 3. 학습 환경 — 헤드리스 .NET 시뮬레이터

Unity 배치모드로 한 판을 돌리면 지금 `FaithSimulation` 기준 24판에 약 5분(판당 ~12초)이고, 같은 프로젝트를 여러 개 띄울 수 없다. 강화학습에는 수만~수십만 판이 필요하므로 **게임 로직만 따로 빌드한 .NET 8 콘솔 프로그램**을 만든다.

- 근거: `Systems`·`Data`·`Core`·`Actions`가 쓰는 UnityEngine API가 얕다 — `Vector2Int`, `Mathf.*`, `Debug.Log*`, `Resources.Load<TextAsset>`, `Color`, `Vector2/3` 몇 곳뿐이다.
- 구성: `tools/TacticsSim/TacticsSim.csproj`가 `Assets/Scripts/TacticsECS/{Core,Data,Systems,Actions}/**/*.cs`를 **링크로 컴파일**(복사하지 않는다 — 규칙의 출처는 하나), `UnityShim/`에 위 타입의 최소 구현. `Resources.Load`는 `Assets/Resources`의 CSV를 파일에서 읽는다.
- 한 판 초기화는 `FaithSimulation.Simulate`의 준비 과정을 공용 함수로 꺼내 Unity 쪽과 시뮬레이터가 같이 쓴다(지금은 Editor 코드 안에 있다).
- 정합성 검사: 같은 시드·같은 규칙 AI로 Unity 배치모드와 시뮬레이터가 **턴별 상태 해시가 같은지** 비교하는 검증을 `VerificationSuite`에 추가한다. 이 검사가 깨지면 학습 결과를 믿지 않는다.
- 파이썬 연결: 파이썬(PyTorch) 학습기가 시뮬레이터 프로세스 N개를 띄우고 표준 입출력(길이 접두 바이너리)으로 "결정 지점의 특징 배열 ↔ 고른 후보 번호"를 주고받는다. 병렬은 프로세스 수로 늘린다.
- 실패 시 대안: 심이 막히면 Unity 배치모드 워커(프로젝트 복사본 여러 개)로 간다. 느리므로 학습 규모를 줄이고 모방 학습 비중을 높인다.

## 4. 학습 절차

1. **모방 학습(BC)**: 규칙 AI끼리 무작위 종족·신·맵 크기·시드로 수천 판을 돌려 (특징, 규칙 AI가 고른 후보)를 모은다. 정책이 규칙 AI를 흉내 내게 지도학습한다. 목표: 규칙 AI 상대 승률 45~55%.
2. **자기 대국 PPO**: BC 정책에서 시작해 PPO로 강화한다.
   - 보상: 승 +1 / 패 −1. 초반에는 턴마다 점수 차 변화(`ScoreSystem`)를 작은 보조 보상으로 주고 점차 0으로 줄인다(점수 따기만 배우는 것을 막는다).
   - 턴 상한을 두고, 넘기면 점수 비교로 판정(학습 전용 — 실제 게임에는 턴 제한이 없다).
   - **리그 상대**: 최신 정책 50%, 과거 스냅샷 30%, 규칙 AI 20% — 한 전략에 갇혀 맴도는 것을 막고 규칙 AI에 대한 회귀를 막는다.
   - 매 판 종족·신·맵 크기·맵 타입·선후공을 무작위로 해서 특정 맵에 과적합하지 않게 한다.
3. **스냅샷 저장**: 일정 간격마다 정책을 저장하고 평가 대상에 넣는다.

## 5. 다섯 단계 만들기 — Elo 사다리

난이도를 감으로 정하지 않고 **측정한 실력**으로 고른다.

1. 후보 풀: 무작위 합법 행동 AI, 실수를 섞은 규칙 AI, 규칙 AI, BC 정책, PPO 스냅샷들.
2. 풀 전체를 라운드 로빈으로 대국시켜(쌍마다 수백 판, 선후공 교대) Elo를 매긴다. 규칙 AI를 기준점으로 고정한다.
3. **인접 단계 상대 승률이 약 70~75%** 가 되도록 다섯 개를 고른다(예상: 1 ≈ 실수 많은 BC, 2 ≈ 규칙 AI 근처, 3·4 = 중간 스냅샷, 5 = 최강 스냅샷).
4. 같은 모델 안에서 미세 조정할 추론 손잡이(난이도 CSV 열):
   - `Temperature` — softmax 온도(높을수록 덜 날카롭게 둔다).
   - `BlunderChance` — 결정 지점마다 이 확률로 상위 후보 대신 차선 후보를 고른다(어이없는 수가 아니라 "덜 좋은 수"를 둔다 — 입문 단계가 이상해 보이지 않게).
   - `Model` — 쓸 가중치 파일 이름. 같은 모델을 여러 단계가 같이 써도 된다.
   - (선택) `SearchDepth` — 5단계만 전투 결정에서 한 수 앞 시뮬레이션(복제한 상태로 공격 결과를 굴려 보기).
5. 사람 플레이 테스트로 1단계가 "처음 하는 사람이 이길 수 있는가", 5단계가 "숙련자도 지는가"를 확인하고 손잡이를 다시 맞춘다. 사다리 수치는 학습을 다시 할 때마다 재측정한다.

## 7. 단계별 일정 (각 단계 끝에 spec 갱신 + 커밋·push)

| 단계 | 할 일 | 끝났다는 기준 |
|---|---|---|
| 0. 준비 | 위키 봇 난이도 조사, 후보 생성/선택 분리 리팩터링(동작 변화 없음) | `FaithSimulation`·`VerificationSuite` 결과가 리팩터링 전과 같다(같은 시드 같은 판) |
| 1. 시뮬레이터 | `tools/TacticsSim` + UnityShim, 판 초기화 공용화, 상태 해시 정합성 검증 | 같은 시드에서 Unity와 시뮬레이터 해시 일치, 판당 시간 측정(목표 1초 이하) |
| 2. 파이썬 연결·특징 | 결정 지점 프로토콜, `PolicyFeatures`, 무작위 정책으로 끝까지 도는 판 | 무작위 정책 1,000판이 예외 없이 끝난다 |
| 3. 모방 학습 | 규칙 AI 데이터 수집, BC 학습, `.bytes` 내보내기, C# 추론 | C# 추론 결과가 PyTorch와 소수 5자리까지 같다, 규칙 AI 상대 45~55% |
| 4. PPO 자기 대국 | 리그, 보상 조정, 스냅샷 | 최강 스냅샷이 규칙 AI 상대 80% 이상 |
| 5. 난이도 사다리 | Elo 평가 도구(`DifficultySimulation`), 5단계 선정, `AIDifficulty.csv` | 인접 단계 승률 70~75%, 단계가 오를수록 단조 증가 |
| 6. 게임 연결 | UI·저장·샌드박스, 단계별 플레이 영상(`record_play.sh`에 난이도 인자) | 모바일에서 AI 한 턴 추론 시간 예산(예: 200ms) 안, 이어하기 후 같은 수를 둔다 |
| 7. 다듬기(선택) | 5단계 탐색, 공간 CNN, 사람 플레이 테스트로 손잡이 재조정 | 플레이 테스트 피드백 반영 |

## 8. 위험과 대응

- **심 정합성 깨짐**: 시스템 코드가 UnityEngine을 더 쓰게 되면 시뮬레이터가 갈라진다 → 정합성 검증을 전체 검증에 넣어 매 커밋 확인.
- **규칙·CSV가 바뀌면 모델이 낡는다**: 표 팩으로 수치를 바꾼 판에서는 학습한 감각이 틀린다 → 모델 파일에 학습 당시 표 팩 ID를 기록, 다르면 경고(그래도 동작은 한다). 큰 규칙 변경 뒤에는 4~5단계를 다시 돌린다.
- **보상 꼼수**(점수만 따고 안 이기기, 끝없이 버티기): 보조 보상 감쇠, 턴 상한 판정, 영상으로 확인([끝까지 보는 플레이 영상](../scripts/record_play.sh)).
- **학습 비용**: 로컬 CPU 병렬로 시작, 판당 시간과 필요한 판 수를 1단계에서 측정한 뒤 GPU/클라우드 필요 여부 결정.
- **입문 단계가 부자연스러움**: 무작위 수 대신 "차선 후보" 방식 + 낮은 스냅샷 사용.

## 9. 먼저 정할 것

1. 사람 쪽 학습 환경: 로컬 PC에서 돌릴지(CPU 코어 수), GPU·클라우드를 쓸지.
2. 2팀 대전만 다룰지(지금 `CitySystem.Teams`), 앞으로 다인전도 대비할지 — 다인전이면 특징·리그 설계가 달라진다.
3. 5단계 탐색(한 수 앞 보기)을 넣을지 — 모바일 추론 시간과 맞바꾼다.
